# Working on Partly

Read this file and the relevant package READMEs before changing the project. They record the supported POC behavior. Keep them current when decisions change. Local proposals, design studies, test output, screenshots, databases, and caches are not tracked in Git.

## Scope and implementation

- Prepare the smallest complete self-hosted alpha. Avoid speculative abstractions, extra services, and features added only for future customers.
- Control plane: Rust, Axum, embedded SQLite, and a vanilla HTML/CSS/JavaScript dashboard bundled into one executable. No required Docker, external database, or frontend runtime.
- SDK order: Python, Rust, Go, then Node.js. All four use the shared Rust evaluator: Python through PyO3, Rust directly, Go through cgo, and Node.js through Node-API. Build standalone Rust crates and platform-specific Go/Node archives with their native libraries; verify them outside the checkout through the shared contract. Registry publishing remains separate. No browser SDK or frontend application example.
- Python support and CI target regular CPython 3.14 only. Build version-specific wheels; do not add other Python versions or free-threaded builds to this alpha.
- Keep one release version across the server and all SDKs, sourced from the root Cargo workspace. Python uses its normalized PEP 440 spelling and Go adds `v`; these are the same release. Keep Node metadata, internal dependency pins, and Go examples aligned. Registry publishing instructions and remaining distribution work are in `docs/publishing.md`.
- Flags return boolean decisions through four rollout modes: everyone, percentage, custom rules, or nobody. Evaluate one flat `context` dictionary; percentage selection uses its stable `id`. Custom rules use plain context keys, with AND within groups and OR between groups. Keep rules inside each flag for now; no reusable audiences, stored profiles, variants, or evaluation-result LRU.
- Keep the Rust evaluator independent of HTTP, storage, and language bindings.
- Release preparation is authorized: versioning, package metadata, binaries, wheels, checks, and operational basics. The PyPI name is `partly-sdk`; `partly.sh` URLs are placeholders until deployed. The user selected ELv2 for the control plane/dashboard and Apache-2.0 for the SDKs, shared evaluator, native bindings, and application integration examples; see docs/licensing.md. Describe the server as source-available and the SDK as open source. Preserve these boundaries and include the relevant license texts and notices in release artifacts. The source repository is https://github.com/ByteBaker/partly. Source pushes are authorized; package registry publication still requires approval. Enterprise features, HA, billing, and premium activation are deferred. SSE is optional.

## Contracts to preserve

- Building a client makes no network calls. `init()`, `refresh()`, and network cleanup are async; initialization failure raises an error. Never block the application's event loop with network work.
- Examples must separate application startup, request handling, and shutdown. Initialize once before accepting requests, keep the client and its policy in application state, and reuse it for local evaluations. Do not put initialization, refresh, or cleanup in request handlers.
- Preserve the Rust URL parser's typed error and source. Keep malformed URL errors separate from allowed-origin validation, and do not include supplied URLs or credentials in diagnostics.
- Flag evaluation is local. Return explicit enabled/disabled decisions; raise specific errors for unknown flags, unavailable policy, or invalid required context. Never silently allow or deny an undefined flag.
- Custom rules are authored in the dashboard and evaluated in Rust. Each condition uses exactly `k`, `op`, and `v`; `k` names a context key. Number operators: `le`, `lt`, `ge`, `gt`, `eq`. String operators: `prefix`, `suffix`, `contains`, `matches` (exact equality), `regex`. Boolean operator: `is`. All string operations are case-sensitive and types are never implicitly converted. No SDK callbacks or free-form code.
- Keep Rust evaluation errors in `Result` and Python errors as specific exceptions. Missing required context raises `InvalidContextError`; wrong context types raise its dedicated subclass `ContextTypeError`, with structured field/operator/type details and no raw context values. The operator dropdown shows each operator's label and type; selecting it sets the value input to a number field, text field, or True/False radios. No separate type selector. Keep the warning about wrong context types.
- Refresh uses `200` with a complete policy or `304` without a body. Keep the last accepted snapshot on ordinary errors; a confirmed `key_revoked` response clears policy and ETag, stops polling, and makes evaluation/init/refresh return a dedicated revocation error until a new client is built; replace policy and ETag only after validation succeeds.
- Support native HTTPS with paired certificate/key flags. Validate TLS configuration before listening; never fall back to HTTP after a TLS failure. Use actual transport settings for Origin checks and Secure cookies, not forwarding headers. Allow custom DNS names only when explicitly configured. The Python SDK uses verified async HTTPX requests; optional `ca_bundle(path)` supplies private trust roots without disabling certificate or hostname checks.
- Missing database at startup means show setup without creating a file. Create and populate it after valid setup submission. Never overwrite an existing invalid database automatically.
- First setup requires a loopback bind. Existing databases may be served remotely. Use a persistent database-path `.lock` sidecar to exclude other Partly processes; never create it on empty first boot or remove it while in use. Reject database files with multiple hard links, which could bypass the path-based lock. Offline password reset preserves all other data. Support graceful SIGINT and SIGTERM shutdown.
- Bound password hashing concurrency and run it outside the database mutex. Limit login attempts by the actual peer IP, ignoring forwarded headers. Return 429 with Retry-After when busy or throttled.
- Applications belong to one environment and select shared flags from that environment. New apps select no flags by default; new flags are not automatically assigned. Generate a short permanent application ID and first named API Key on app creation; support multiple keys for rotation. SDK builders require environment and application ID, and the server binds each key to that exact pair. Validate downloaded scope from the first policy onward.
- Generate named SDK keys in the dashboard. The authenticated key list includes secrets; keep them in masked fields and copy or reveal locally, without a `/reveal` endpoint. Keep key IDs internal, but show application IDs with Copy ID. Show identifiable masked prefixes/suffixes. Revoked keys remain in a collapsed history with dates and no reveal/copy; return null for their secrets and retain only a hash plus a partial identifier. Plaintext SDK-key storage in SQLite is explicitly allowed for the POC; admin passwords must still be hashed. Do not log credentials.
- Keep the database schema at v1; do not add a migration to this alpha. The released v1 format becomes a compatibility baseline. Later schema changes need a tested, data-preserving upgrade path. Never reset existing databases automatically. Test stopped backup/restore with flags, keys, and admin access.
- Mark the key-storage limit in code: `shortcut: SDK keys are plaintext in the local POC, add protected storage before production use.`

## Quality and documentation

- Keep shared code under `crates/` and language-specific SDK implementations under `sdk/<language>` (`python`, `rust`, `go`, `node`). Keep application examples under `examples/<language>`. Add folders when implementing them, not as empty placeholders.
- Keep frontend check configs and development requirements in `config/`, Python check settings in the root `pyproject.toml`, guides in `docs/`, and server dependency notices in `licenses/`. Run frontend checks through `npm run lint` and `npm run typecheck`. Keep workspace manifests, LICENSE, and NOTICE at the root; preserve the existing filenames inside release archives.
- Keep the blue Console design: compact layout, white and neutral surfaces, restrained blue accents, clear borders, readable controls, and keyboard accessibility. Avoid gradients, decorative shadows, and generic AI-style decoration.
- Use direct tool labels instead of slogans, decorative section labels, or repeated technical metadata. Keep the default project internal. Environment names are labels; do not give production special UI treatment or show environment warning banners. Align Create flag and Create app in the same page-header position; use deliberate creation dialogs.
- Preserve the Partly logo. Keep the brand, environment selector, and tab ribbon together in a sticky header. Success feedback must not move or resize existing content when it appears or disappears. Use existing space beside the affected item or an anchored tooltip, with short labels such as Copied, Saved, or Created. Never insert a message row or page banner for success feedback.
- Call application credentials API Keys in the UI. Explain that API Keys read flags and rules, while edits are made through the UI. Use the established builder conventions for required environment/application settings.
- Keep four dashboard screens in this ribbon order: Feature flags, Apps & Keys, Audits, Docs. Docs offers Python (default), Rust, Go, and Node.js, using the runnable files in examples/ with syntax colors, placeholder URL/API key constants, and an accessible copy icon. Test the served snippets against the real SDKs. Do not show installation steps or require environment variables in the quickstart. Disable copying while an example is loading or unavailable.
- Keep the environment selector at the top right. The environment is part of the URL; switching environments reloads the page. Warn before losing unsaved edits through navigation, reload, or closing a dirty modal.
- Use styled dropdowns throughout the dashboard, including their option menus. Preserve keyboard navigation, type-ahead search, accessible labels, and selected states. Opening menus must not move content. Escape and outside clicks cancel the pending choice.
- Use styled modal dialogs for app confirmations and warnings, never browser alert/confirm/prompt popups. Focus the safe action first and support Escape to cancel. Keep browser-managed beforeunload protection for unsaved edits on reload or tab close; browsers cannot replace it with a custom modal.
- Create flags through a modal in the current environment only. Display the environment as read-only context, never as a selectable field. Create and edit responses return the saved flag so the dashboard can update it in place without refetching the list or discarding other drafts.
- Before saving or deleting an existing flag, always show affected applications (or “No applications use this flag.”) and require the exact case-sensitive `environment/flag_name`, highlighted in the prompt. Validate confirmation on the server; stale flag/assignment previews must be reviewed again.
- Record successful flag, application, assignment, and key changes on the backend, in the same transaction as the change. Audit entries include the admin account, time, action, typed item, before/after values where applicable, and affected applications at that time. Never audit complete secrets/passwords. Audit history is read-only through the API, environment-scoped, paginated, and filterable by action/application. One admin account cannot identify teammates sharing credentials.
- Display audits as readable states, with before → after transitions for changes. Creation shows only the initial state; deletion shows the removed state. Never display raw JSON or null snapshots in the dashboard. Keep audit columns balanced and stack state transitions on small screens.
- Write READMEs in CEFR-B2 English. Explain necessary terms and provide working examples.
- Start first-party code files with `Copyright 2026 ByteBaker` and the component's SPDX license identifier in language-appropriate comments. Preserve required shebangs and doctypes; leave generated and third-party material unchanged.
- Keep the root README focused on what Partly does, getting started, key alpha limits, and links to package and release guides.
- Keep the existing logo and a real dashboard screenshot with sample data under `docs/images` for the root README. Test screenshots and other generated test output stay untracked.
- Keep `examples/python` runnable and exercise it through end-to-end tests. Start with a minimal working quickstart; keep detailed options and error types in the SDK reference. Cover all supported POC workflows, including setup, keys, async SDK lifecycle, refresh, and failures.
- Add focused tests for native evaluation and percentage consistency. Run checks appropriate to each change; documentation-only edits do not require application tests.
- Keep CI tiers independently runnable and reusable: lint/types, verification, build-and-test, then release artifacts. PRs and main pushes stop at verification: formatting, Ruff, strict mypy, ESLint, TypeScript without emit, Biome CSS checks, HTML-validate, ShellCheck, actionlint, Clippy, Go vet/Staticcheck, and vulnerability scans. Clippy supplies Rust compiler checks; do not duplicate them with cargo check or build product artifacts on routine PRs. Keep Python SDK and native stub types accurate; ship `py.typed`.
- Explicit builds call verification before compiling, then run unit tests, the shared SDK contract, and Chromium E2E. Version tags and manual release runs call build-and-test, then add minimum-version checks, other browsers, license validation, and Linux/macOS artifacts. All prerequisites must pass. Compiler checks do not replace linking, packaging, or runtime tests before release.
- Run RustSec, pip-audit, govulncheck, and npm audit for PRs/releases and daily. Do not suppress findings to make CI green. Use patched supported toolchains for release builds and security scans; older minimum versions belong only to compatibility checks.
- Add SDKs against the shared contract in `tests/e2e/test_sdk_contract.py`, in Python, Rust, Go, then Node.js order. Language drivers in `tests/sdk_contract/` call real SDK APIs. Missing SDKs or toolchains must fail, never skip or xfail; keep failing work uncommitted and commit only after the applicable checks pass.
- Do not claim performance gains without measurements that include Python binding overhead.
- When research is needed, use primary sources and the strongest available research model where model selection is supported.
